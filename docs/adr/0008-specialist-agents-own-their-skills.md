# Specialist agents own their skills

A specialist agent carries skills and MCP servers that no other agent sees, because every installed skill's description and every MCP tool's schema costs context on every turn in every harness, and a domain pack like the 94 Blender skills or fal's media tools is useless outside its domain. Bundles are listed in `agents/skill-sources/bundles.nix` by bundle name, so several repos can feed one bundle; they are fetched and locked like skills and never merged into `~/.agents/skills`. Bundling clears `disable-model-invocation`, because a specialist works from a brief with no human to type a skill's slash command. `agent-skills` pairs each role prompt in `agents/specialists/<name>.md` with its bundle, if any, as `config.lib.agents.specialists.<name>`.

- A specialist is a `pi.specialists.<name>` entry (the `pi-specialists` aspect), declared in the aspect of the app it drives: `blender` and `kaigen-studio` declare theirs, and `agent-specialists` holds those with no app aspect (media, cloudflare, ui, qa). Each becomes the command `pi-<name>`: Pi run as the main agent with only its bundle (`--no-skills --skill`), its tools, its role prompt, no context files or prompt templates, and its own agent directory `~/.pi/specialists/<name>`. Pi is the one harness here that takes all of that as flags.
- The specialist's MCP servers live only in its agent directory's `mcp.json`, which Nix owns outright because nothing else writes it (OAuth tokens go to `mcp-auth.json`), with tools declared directly and filtered to its servers by `--tools mcp__<server>__*` (Pi turns `-` in a server name into `_`). `--no-approve` keeps a trusted project's `.pi/` files from replacing those servers. A separate agent directory is the only way Pi keeps one session's servers out of another, and it also keeps each specialist's OAuth sign-ins and sessions apart: `pi-<name> mcp login <server>` signs in once. Its settings reuse the main Pi's Claude provider, and the command passes the model as `--model` instead of a settings default: Pi picks a default model before the provider's async `claude auth status` check finishes, so about a third of runs found no model or fell back to another logged-in provider, while an explicit `--model` waits for the check. A caller's own `--model` still wins.
- It is not a pi-subagents agent, because since 0.43 pi-subagents runs every child through `workflowScript`, which needs `node:v8` promise hooks that the Bun-built Pi lacks. Claude Code's `skills:` field only preloads and Codex agents can only disable inherited skills, so in those harnesses a specialist would read its bundle through an index instead.
- The Blender specialist drives the headless Blender CLI, not Blender MCP: the skills' real work is `bpy` code either way, and the MCP add-on needs a running GUI Blender listening on an unauthenticated socket that executes any Python it receives. The role prompt translates the skills' MCP calls into CLI steps and preview renders.
- Orchestrators call `pi-<name> -p "<brief>"`; run bare, it is an interactive session. T3 Code runs each as its own Pi provider instance (the Pi driver's `binaryPath`), so an orchestrator delegates to it as a visible child thread. `pi-specialists` declares those instances through `t3code.providerInstances`, which `t3code-settings` merges into `~/.t3/userdata/settings.json` at activation for every user that declares one, desktop or headless service alike, instead of owning the file, because T3 writes the rest of it.
- Design skills (jakubkrehel, emilkowalski, vercel-labs/ui) belong to the `ui` specialist alone; general sessions keep only the `frontend-ui` skill, which hands design work to `pi-ui`.
