# Hermes cross-profile ops

## When to use

Cross-profile work: sending a task brief to a specialist profile (homelab, coach, household) from this default profile, checking what the specialist actually did, or delivering a message the specialist cannot send itself (Patrick's Signal, group chats).

Run specialist work from the default profile over the CLI, verify it from the specialist's own records, and relay notifications the specialist cannot send itself.

## Invoking a specialist profile

Use `hermes -p <profile> chat --query-file <brief-file> --oneshot`. Pass the brief as a file: a long multiline `-q` argument gets mangled by shell parsing, as if one of its lines were a subcommand.

Run investigations and cleanup jobs that may take several minutes as tracked background terminal jobs with completion notification. A foreground wrapper timeout can interrupt the specialist's active tools before it produces a result. Include absolute report and raw-evidence paths in the brief so findings and measurements can be recovered without relying on the terminal output tail. Check whether the background launch actually enabled completion notification. If the runtime explicitly cannot deliver notifications, keep the invocation tracked and use bounded process waits until it exits; a wait timeout with process_running=true is not a failed specialist run and must not trigger a duplicate invocation. On completion, inspect the report and session records, independently verify any external changes, then relay the result to Patrick.

If a wrapper times out, check whether its process is still alive and inspect that invocation's session records before retrying. Do not launch a second cleanup while the first might still be deleting files. Recover partial measurements as partial results, not as proof that the specialist completed its task.

## Updating profile configuration

1. Enumerate existing profile directories and read each profile's `config.yaml` plus the root `~/.hermes/config.yaml` before changing settings. Root MCP servers may be shared by the gateway, while profile-local config can override or hide them; never infer one scope from the other.
2. For MCP access, identify the actual consumer first: standalone CLI session, profile-local session, or already-running multiplexed gateway. From a specialist process, explicitly use `hermes -p default mcp list` for the root/default consumer and `hermes -p <profile> mcp list` for the specialist; an unqualified command can inherit the specialist's profile. Inspect the Nix source when configuration is declarative. Preserve unrelated settings and confirm any referenced secret is available to the process that will connect. For custom remote MCP installation and persistence checks, follow [Custom MCP installation](references/custom-mcp-installation.md).
3. Before changing a profile's model, read its effective `model` config and find its source of truth. Confirm the exact model ID in the intended provider's catalog, then check both `hermes -p <profile> auth list` and `hermes -p <profile> auth status <provider>`; an auth-list entry alone can reflect an environment-variable source even when the provider is logged out. Change model and provider together, and remove a stale `base_url` or API mode when it belongs to the old provider. A cache entry under a different provider does not validate the requested provider/model pair, and OAuth providers may have no cache entry at all; when the catalog cannot confirm the ID, validate the pair with the one-shot usage report (rule 5) instead of hunting the cache.
4. The home-manager refusal fires even for `hermes -p <profile> config set`; do not retry with flags. The nix module (`nixos-config/modules/aspects/agent/hermes/config.nix`, `services.hermes-agent.settings`) generates only the root config; named profiles' `config.yaml` files are plain files no switch regenerates (activation scripts perl-patch only specific keys). So a profile-scoped change is a direct edit of that profile's `config.yaml`, preserving unrelated keys and keeping the edit scoped so shared defaults are untouched. Reserve the nix module for root/shared settings.
5. Smoke-test a model change with a short one-shot invocation through the target profile, without a model override, and inspect its usage report to confirm the resolved model and provider. If provider resolution or authentication fails, restore the previous working model/provider rather than leaving the profile pointed at an unusable route. Then verify `hermes -p <profile> config get model` and distinguish that fresh CLI result from any already-running multiplexed gateway's loaded configuration.
5. Verify the MCP connection and discovered tools with `hermes -p <profile> mcp test <server>` and a one-shot tool call. These checks prove only that a newly launched CLI process can connect. They do not prove an active gateway session has the same configuration, credential, or tool schemas.
6. After adding profile-local MCP configuration, use `/reload-mcp` in that profile's existing chat to reconnect servers and refresh cached agents without losing conversation history. The reload is profile-scoped under multiplex. Do not restart the gateway from a command running inside it; the runtime blocks this because restarting would terminate its own child command. Fresh CLI discovery does not refresh an existing Signal session.
7. When validating MCP access, distinguish tool exposure from response validity. A real tool invocation returning a `CallToolResult.structuredContent` dictionary validation error proves the tool is exposed but the server returned invalid structured content. Do not report the integration as working or bypass validation as a fix.
4. For gateway or Signal failures, inspect the correct gateway logs for MCP connection/authentication errors, compare process lifetime/configuration with current secrets without printing secret values, and confirm whether a restart or reload is needed. After it, verify the gateway connection and an actual tool call from a fresh session on the target route. Do not claim success from config display or an isolated CLI probe alone. Check shared credential availability with `hermes -p <profile> auth list` when changing providers.

A background process wrapping this call returns only an output tail. Verify the actual result from the specialist profile's own records (`~/.hermes/profiles/<name>/state.db` messages table, filtered by the session ID the process output names) — the tail can omit the specialist's real reply and any failed tool calls.

### Repairing an expired provider API key (HTTP 401)

When gateway/status notifications show a provider returning `401 ... This API key has expired` while the same provider still works from another profile, the stale secret is per-profile, not global:

1. Locate the secret and the credential state. Each profile's `.env` holds it (e.g. `OPENCODE_GO_API_KEY`); `profiles/<name>/auth.json` `credential_pool` entries share one credential id across profiles and carry `secret_fingerprint` plus `last_status='exhausted'` and the provider error. The working profile's fingerprint is the reference; stale profiles can be enumerated by comparing fingerprints across all profile dirs in one pass.
2. Repair each stale profile: back up its `.env` under the profile's `backups/`, replace the key value without ever printing it, set `secret_fingerprint` to `sha256:` + the first 16 hex chars of sha256(key) (this is the derivation — validate by matching the working profile exactly), and delete `last_error_code`, `last_error_message`, `last_error_reason`, `last_error_reset_at`, `last_status` (and companions) from the credential entry, then bump `updated_at`.
3. Verify before restarting: probe the provider endpoint directly with the copied key (Bearer; include any header the endpoint requires) and require HTTP 200. A key check that only changes files teaches you nothing about whether the old fingerprint-mapping logic accepted the new key.
4. Restart the gateway (`systemctl --user restart hermes-agent.service`) — `.env` is read at process start, so the switch is inert until then. The profiles share one gateway process (check the pid in any profile's `gateway.lock`, which also names the `hermes_home`). 'Do not restart the gateway from a command running inside it' applies — a restart issued from a session kills that very turn; run it as the last act and expect Patrick to see an interruption bubble.
5. Read back every repaired `auth.json` (fingerprint matches, status cleared) once the gateway is up.

## Brief construction

For live advice from the coach, send the question to `hermes -p coach chat --query "..." --oneshot`, explicitly asking for current training and workout/recovery context and forbidding plan or record changes unless requested. Include any user correction that changes the premise, such as an intention to run despite an earlier recommendation not to; do not let a stale answer stand in for the updated question. When workouts or recovery materially affect advice, ask for a concrete duration and effort target and whether a workout already logged counts. Relay the coach's answer concisely, preserving its recommendation and safety caveats.

For other specialist tasks, build the brief from tool output read during the session, not from recall: what is installed, what version, what is disabled. Include the verified source URL so the specialist does not re-research. When Patrick shares a goal or intention with a profile without specifying a concrete task, relay that context and ask the profile to offer one practical next step or a focused planning question. Explicitly prohibit purchases, bookings, or other commitments unless Patrick asked for them. Relay the profile's useful answer directly and briefly.

When Patrick says "do not act on this yet", the brief still authorizes read-only research plus delivering the answer to Patrick, but nothing that writes state. State that boundary explicitly in the brief; specialists do not infer it.

For a quick status question ("how is nika", anything asked by voice), the homelab snapshot script is the whole check: one round trip, a short spoken answer. For host-health diagnosis, require short interval samples and separate resource availability from actual activity. Ask the homelab specialist to compare load with CPU count, CPU busy time with I/O wait and pressure, and available RAM with swap-in/out rather than treating occupied swap as a shortage. For GPUs, require driver/device discovery, utilisation and process evidence; container resource advertisement alone is not proof of compute execution. For spare disks, require model, filesystem, mount status and workload use; an unmounted disk is not evidence that it is empty. Keep mounting, formatting and test workload launches outside a read-only brief. Require the specialist to preserve timestamped raw measurements alongside the concise report. When pressure and device activity disagree, require a second simultaneous interval sample before attributing a bottleneck; high I/O PSI alone does not prove disk throughput saturation or hardware failure. Require explicit visibility limits for privileged logs and SMART, and distinguish historical log errors from current-boot failures. Treat an unavailable endpoint as an observation until its intended running state is confirmed. Relay the measured bottleneck and sampling limitations rather than declaring the whole machine healthy from service status.

## Notification relay

Friendly targets like `signal:Patrick` are a default-profile alias; specialists cannot resolve them and `hermes send` fails with "Could not resolve 'Patrick'". To have a specialist deliver a message itself, put the explicit E.164 target (`signal:+4551718923`) in the brief. Verify the send from the specialist's own session record or gateway/agent.log (a `send_message Signal: ... in N batch(es)` line at the send timestamp), not from its self-report alone.

A platform that works from the default (e.g. Signal) may still be fully unconfigured on a specialist — the send then fails with "no targets". Do not stand on the notification requirement; fall back to sending from this profile with `hermes send --to signal:Patrick` and report that you relayed it.

Prefer `hermes send` over an agent one-shot for mechanical delivery: it needs no model, so provider rate limits and agent turns do not block it. Discover delivery configuration with `hermes -p <profile> send --list` rather than assuming named profiles have their own platform credentials. When a multiplexed gateway owns delivery, resolve the explicit target from `gateway.profile_routes` in the root `~/.hermes/config.yaml`, not the declarative source, which may contain unresolved placeholders. Use the default profile for an immediate send when that is the configured sender. Pass short message text positionally, as `hermes send --to signal:Patrick 'Message text' --json`, or use `--file <path>` for a prepared text report. Attachments ride in the message text as `MEDIA:<absolute path>`; `--file` is text-only. Confirm a direct send with the `--json` result, including success and chat_id.

Send one completion report per destination. When `hermes send` delivers the full result to the current Signal chat, do not repeat that report in commentary or the final reply. If a separate completion ping is required, keep it brief and put the detailed findings in only one subsequent message; duplicate deliveries obscure which report is authoritative.

## Profile-owned scheduled reminders

1. Confirm the requested owning profile and recipient before writing. Use `hermes -p <profile> cron list --all` to avoid duplicates, inspect the root `gateway.profile_routes` for the recipient's explicit platform/chat identifier, and run `hermes -p <profile> cron status` to verify the scheduler serving that profile. Do not put a named profile's job in the default profile merely because the current chat belongs there.
2. Resolve timezone intent before scheduling when an abbreviation changes the result. Distinguish fixed CEST, UTC+02:00, from Danish local time, Europe/Copenhagen. Ask when necessary; then inspect the actual scheduler timezone with configuration and `readlink -f /etc/localtime`. A displayed UTC offset alone does not establish daylight-saving behaviour.
3. For a fixed reminder, use a profile-local shell script and `--no-agent` rather than an autonomous model session. Write only the agreed reminder text to stdout with `printf '%s\\n' 'Reminder text'`, then run the script locally to verify its output without messaging the recipient. This avoids model cost, paraphrasing, and provider dependencies. Do not add medication doses or advice the user did not request.
4. Store the script under the owning profile's `scripts/` directory and pass its relative filename to `--script`; the cron CLI validates paths relative to that directory. For a scheduler verified to use the requested local timezone, create with `hermes -p <profile> cron create '0 22 * * *' --name '<name>' --script reminder.sh --no-agent --deliver 'signal:<verified-chat-id>'`. Use an explicit delivery target so the job cannot inherit the coordinator's origin chat. Choose failure delivery deliberately rather than sending operational errors to the reminder recipient by accident.

When the owning profile has no configured platform for that recipient (job history shows 'ran, but the result was not delivered — platform not configured/enabled'), do not leave the `--deliver signal:<id>` target in place: set `--deliver local --failure-deliver local` and put the actual delivery inside the `--no-agent` script as `hermes -p default send --to 'signal:<verified-chat-id>' --json` (the root/default profile owns the working Signal route; verify the chat id against `gateway.profile_routes`). Gate the send behind a `--preview` flag that only prints, so step 3's local verification run can never message anyone.

For a one-shot reminder, an absolute timestamp like `2026-11-02T08:00:00+01:00` schedules once; `--repeat 1` is redundant and harmless.
5. Read back `hermes -p <profile> cron list --all` and the exact job record under that profile's `cron/jobs.json`, then run `hermes -p <profile> cron doctor`. Confirm enabled state, recurring schedule, next execution, script, no-agent mode, and recipient. Do not manually trigger a live reminder merely to test scheduling unless the user authorized an immediate message.
6. Report creation and schedule verification separately from delivery verification. An active job and a passing doctor check establish scheduling readiness, not that a Signal message has already arrived; inspect run history and delivery evidence after an actual execution before claiming end-to-end delivery.

## Cleanup discipline

For delegated disk cleanup, separate diagnosis from authorization. Include measured paths, explicitly authorized deletions, retention requirements, and protected data in the execution brief. Require before-and-after filesystem usage plus readback of the affected paths or retained generations. Treat directory sizes as occupied space, not guaranteed recovery, and do not attribute changing free space to the cleanup without deletion output supporting it.

When briefing Nix cleanup, distinguish generation pruning from store reclamation. Require the specialist to inspect GC roots if collection frees unexpectedly little, including temporary roots held by an active optimiser. Do not authorize deleting live roots to force reclamation. If stopping a standalone optimisation unit is within scope, require identification of its owning unit and restart policy, graceful stop, then GC and verification that running/current system targets and workloads are unchanged. Preserve the user's generation-retention policy across follow-up requests; do not prune another generation merely because the user asks for more space.

Require cleanup reports to separate Nix's reported reclaimed bytes from the whole-filesystem `df` delta, because unused-link removal and concurrent activity can make those totals differ. Label GB versus GiB consistently and report remaining free capacity alongside recovered space. For follow-up space inventories, request privileged accounting of root-owned directories as well as the user's home, and distinguish regenerable caches from installed tools and application state before recommending deletion. Treat permission-limited totals as lower bounds, not complete directory usage. Require mount-aware accounting on Kubernetes hosts: `du -x` still traverses same-device bind mounts, so exclude kubelet pod aliases when counting the underlying persistent volumes. Measure swap files and filesystem-reserved blocks separately; reserved capacity reduces available space but is not occupied application data. Avoid adding independently scanned hardlinked directory totals as though each represents unique disk blocks.

A probe interrupted mid-download can still leave files on disk. Track what an aborted call might have created (e.g. an npx cache fetched to satisfy a `--version` probe) and clean it yourself when Patrick asks — do not leave him to find the artifact later.
